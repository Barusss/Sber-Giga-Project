# Реальные ТУ (транскрипция) + синтетическое ЗнП (2250 кВт, 10 кВ)

Пара для ручной проверки модуля ТУ ↔ ЗнП: **очищенная транскрипция реальных ТУ** на технологическое присоединение и **синтетическое ЗнП**, составленное под их параметры.

Оригинал ТУ — локальный PDF `Технические условия на присоединение к электрическим сетям.pdf` в папке `Downloads` (ПАО «МОЭСК», 2250 кВт, 10 кВ, II категория). В репозиторий он не добавлен: в документе есть подписи, ФИО и реквизиты. Номер ТУ в скане читается неуверенно, для матчинга он не важен.

## Что внутри

| Файл | Назначение |
|---|---|
| `tu_transcription.docx` | Чистая транскрипция ключевых пунктов реальных ТУ для загрузки в UI |
| `znp_synthetic.docx` | Синтетическое ЗнП для загрузки в UI |
| `tu_transcription.md`, `znp_synthetic.md` | Человекочитаемые версии документов |
| `scenarios.json` | Payload для `/requirements/analyze` и ожидаемые статусы |
| `run_scenarios.py` | Офлайн-самопроверка на детерминированном fallback, без API-ключа |

В DOCX заголовок и дисклеймер вынесены в колонтитул, а в теле оставлены только нумерованные пункты. Так парсер не создаёт лишние «требования» из заголовков и подписей.

## Почему ТУ в виде транскрипции

Оригинальный PDF — скан с очень плохим OCR: парсер извлекает латиницу и обрывки текста вместо кириллицы. Если подать его в матчинг, тест будет проверять качество OCR, а не логику сопоставления. Поэтому для пары используется ручная транскрипция ключевых пунктов:

- параметры и этапы мощности сохранены;
- ФИО, подписи, адреса и реквизиты удалены;
- название заявителя обезличено;
- текст упрощён и не является юридической копией ТУ.

Оригинальный PDF можно отдельно использовать для проверки OCR/парсера, но не для оценки матчинга.

## Параметры пары

- максимальная мощность — 2250 кВт;
- напряжение — 10 кВ;
- II категория надёжности;
- этапы: 625 / 875 / 1125 / 2250 кВт;
- точка присоединения — вновь сооружаемая ячейка РП-10 кВ;
- учёт — трёхфазный прибор класса точности 0,5S;
- компенсация реактивной мощности — предусмотрена;
- резервирование 4 этапа — от ПС ЛБ802 и ПС ЛБ264.

## Намеренные отклонения в ЗнП

ЗнП в основном повторяет ТУ, но содержит контролируемые расхождения и пропуск:

| Пункт ТУ | В ЗнП | Ожидаемый статус |
|---|---|---|
| 3 этап — 1125 кВт | 3 этап — 1000 кВт | `needs_review` |
| II категория | III категория | `needs_review` |
| класс точности 0,5S | класс точности 1,0 | `needs_review` |
| компенсация реактивной мощности | пункт отсутствует | `missing` |

Остальные требования должны быть `fulfilled`. Итого: **7 `fulfilled`, 3 `needs_review`, 1 `missing`** (11 требований).

## Быстрая офлайн-проверка

Из корня репозитория:

```powershell
python docs\manual-test\real-tu-2250\run_scenarios.py
```

Скрипт запускает настоящий `RequirementsAgent` с принудительным отказом LLM, поэтому проверяется детерминированный fallback. API-ключ и сеть не нужны. В конце будет `OK` или список несовпадений.

## Проверка через API

Запустите backend и откройте Swagger:

```text
http://localhost:8000/docs
```

Нужен эндпоинт:

```text
POST /api/v1/requirements/analyze
```

В `scenarios.json` у сценария есть объект `payload`. Его можно целиком вставить в тело запроса. Например, для PowerShell:

```powershell
$scenarios = Get-Content docs\manual-test\real-tu-2250\scenarios.json -Raw | ConvertFrom-Json
$body = $scenarios.'real_tu_2250'.payload | ConvertTo-Json -Depth 10
Invoke-RestMethod `
  -Method Post `
  -Uri http://localhost:8000/api/v1/requirements/analyze `
  -ContentType 'application/json' `
  -Body $body
```

## Проверка через UI

1. Откройте `http://localhost:5173`.
2. Создайте проект или откройте существующий.
3. В разделе «Документы» загрузите:
   - `tu_transcription.docx` с типом `tu`;
   - `znp_synthetic.docx` с типом `znp`.
4. Перейдите в раздел «ТУ ↔ ЗнП», выберите проект и запустите анализ.
5. Сверьте статусы с таблицей выше.

## Что важно знать

- **Не отправляйте оригинальный PDF во внешнюю LLM.** В нём есть персональные данные и подписи. Для внешнего API нужна отдельная анонимизация и разрешение.
- **LLM-путь может давать другие статусы для пограничных случаев.** Явные расхождения параметров должны оставаться `needs_review`; пропуск компенсации реактивной мощности должен оставаться `missing`.
- **Пара проверена и с включёнными embeddings.** На модели `paraphrase-multilingual-MiniLM-L12-v2` статусы не меняются: semantic-канал не «спасает» пропущенную компенсацию реактивной мощности.
- **Формулировка категории** в транскрипции — `II категория`, потому что валидатор ищет число перед словом «категория». Формулировку `категория — II` он может не распознать.
- **ЗнП синтетическое.** Оно не является реальной проектной документацией и не предназначено для инженерного использования.
