# Синтетические данные для ручной проверки ТУ ↔ ЗнП

Все документы и тексты в этой папке **синтетические**. Они не являются реальными ТУ, ЗнП или проектной документацией. Персональных данных и коммерческой тайны здесь нет, поэтому файлы можно безопасно отправлять в тестовый API/LLM. Для реальных документов нужно отдельное разрешение и анонимизация.

## Что внутри

| Файл | Назначение |
|---|---|
| `scenarios.json` | 4 готовых сценария: payload для `/requirements/analyze` + ожидаемые статусы |
| `tu.md`, `znp.md` | Человекочитаемые версии основного синтетического ТУ и ЗнП |
| `tu.docx`, `znp.docx` | Те же документы для загрузки через UI |
| `run_scenarios.py` | Офлайн-самопроверка на детерминированном fallback, без API-ключа |

`tu.docx` и `znp.docx` соответствуют сценарию `04_combined_document`. В DOCX заголовок и дисклеймер вынесены в колонтитул, а в теле оставлены только нумерованные пункты: так парсер не создаёт из заголовков лишние «требования».

## Сценарии

| Сценарий | Что проверяет | Ожидание без embeddings |
|---|---|---|
| `01_happy_path` | Полное совпадение мощности, напряжения, категории, класса точности и заземления | 5 `fulfilled` |
| `02_parameter_mismatches` | Расхождения по мощности, напряжению, категории и классу точности | 4 `needs_review`, 1 `fulfilled` |
| `03_missing_and_semantic` | В ЗнП нет напряжения; точка присоединения передана парафразом; огнезащита отсутствует | 1 `needs_review`, 2 `missing` |
| `04_combined_document` | Основной сценарий для `tu.docx` / `znp.docx` | 4 `fulfilled`, 1 `needs_review`, 2 `missing` |

Для сценариев `03` и `04` при включённых embeddings `tu-connection` должен перейти из `missing` в `needs_review` (semantic-only), потому что лексического пересечения нет. Остальные статусы ожидаются без изменений. Это ожидаемое поведение, а не ошибка.

## Быстрая офлайн-проверка

Из корня репозитория:

```powershell
python docs\manual-test\tu-znp\run_scenarios.py
```

Скрипт запускает настоящий `RequirementsAgent` с принудительным отказом LLM, поэтому проверяется детерминированный fallback. API-ключ и сеть не нужны. В конце будет `OK` или список несовпадений. Скрипт проверяет JSON-payload'ы; путь с загрузкой DOCX проверяется через UI.

## Проверка через API

Запустите backend и откройте Swagger:

```text
http://localhost:8000/docs
```

Нужен эндпоинт:

```text
POST /api/v1/requirements/analyze
```

В `scenarios.json` у каждого сценария есть объект `payload`. Его можно целиком вставить в тело запроса. Например, для PowerShell:

```powershell
$scenarios = Get-Content docs\manual-test\tu-znp\scenarios.json -Raw | ConvertFrom-Json
$body = $scenarios.'01_happy_path'.payload | ConvertTo-Json -Depth 10
Invoke-RestMethod `
  -Method Post `
  -Uri http://localhost:8000/api/v1/requirements/analyze `
  -ContentType 'application/json' `
  -Body $body
```

Для сценария `04_combined_document` можно вместо payload загрузить `tu.docx` и `znp.docx` в проект и запустить анализ из UI.

## Проверка через UI

1. Откройте `http://localhost:5173`.
2. Создайте проект или откройте существующий.
3. В разделе «Документы» загрузите:
   - `tu.docx` с типом `tu`;
   - `znp.docx` с типом `znp`.
4. Перейдите в раздел «ТУ ↔ ЗнП», выберите проект и запустите анализ.
5. Сверьте статусы с таблицей выше.

## Что важно знать

- **LLM-путь может давать другие статусы для пограничных случаев.** Главное — явные расхождения параметров не должны оставаться `fulfilled`: валидатор должен перевести их в `needs_review`. В сценарии `03` LLM может ошибочно согласиться с мощностью, но обязан получить `needs_review` из-за отсутствия напряжения в ЗнП.
- **Semantic-сценарий требует включённых embeddings.** Нужны `EMBEDDING_ENABLED=true` и установленный `fastembed`. Без них `tu-connection` будет `missing`, потому что лексического пересечения нет.
- **Номера пунктов не должны влиять на совпадение.** Лексический поиск теперь отбрасывает ведущий номер вида `4.2.` перед сравнением текстов, иначе одинаковый номер у разных пунктов давал ложный бонус. Это закреплено regression-тестом.
- **Категория надёжности** в синтетических текстах записана как `II категория`. Валидатор ищет число перед словом «категория». Формулировку `категория — II` он может не распознать — это известное ограничение, а не ошибка данных.
- **Не используйте эти документы как инженерные или юридические.** Это только тестовые примеры.
