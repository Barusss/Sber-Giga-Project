# Предварительная оценка бюджета DeepSeek перед полной сверкой

Цель: не тратить деньги на запуск, который заведомо не укладывается
в установленные ограничения запросов. Алгоритм НЕ увеличивает лимиты
и НЕ оценивает денежную стоимость — количество запросов и токенов отличается.

## Как работает

Перед первым вызовом DeepSeek в **полной** сверке система считает:

- исходные атомы ЗнП до семантического разбиения;
- сколько из них допускается к семантической атомизации (по тем же
  детерминированным условиям, которые использует рабочий код);
- число требований ТУ и обязательных условий;
- заданные `REQUIREMENTS_LLM_MAX_CALLS`,
  `REQUIREMENTS_LLM_ATOMIZATION_CALLS` и
  `REQUIREMENTS_LLM_TARGETED_CALLS`.

**Расчётный baseline**: число допустимых к DeepSeek-атомизации положений
+ число исходных атомов ЗнП.

Допущение: после атомизации каждый исходный атом требует хотя бы одного
matching-вызова. Это **плановая оценка**, не математическая нижняя
граница: поиск иногда может не найти кандидатов, а атомизация иногда
создаёт дополнительные атомы. Coverage и targeted добавляют запросы
сверх этого baseline, их число заранее точно неизвестно.

Если общий лимит ниже baseline или лимит атомизации ниже числа
допущенных положений, полная сверка отказывается начинаться с HTTP 422.
Ни одного запроса к DeepSeek на этой попытке не выполняется; уже
сохранённые результаты не меняются.

Если лимиты позволяют начать, это **не гарантия завершения**.
Дополнительно журналируются предупреждения, если targeted-cap меньше
числа требований, а общий лимит меньше baseline + число обязательств.

| Дефолтный общий cap | 250 |
| Дефолтный atomization cap | 40 |

При этих настройках preflight блокирует запуск **до расходования API**.
Для полного прохождения потребуется осознанно настроить лимиты
с учётом реальной нагрузки. В предыдущем почти полном запуске
расход составил 923 попытки, но после изменения атомизации это число
может измениться.

## Проверить локально без API

В каталоге проекта `D:\Sber` (пути на документы заменить своими):

```powershell
docker compose run --rm --no-deps `
  -v "${PWD}/diagnostic-inputs:/inputs:ro" `
  -v "${PWD}/diagnostics:/diagnostics" `
  api python -m scripts.diagnose_deepseek_pair `
  --tu /inputs/tu.docx --znp /inputs/znp.docx `
  --out /diagnostics --dry-run
```

В `report.json` / консольном JSON появится `budget_plan` с полями
`blockers`, `warnings` и `assumptions`. Флаг `--dry-run` не
выполняет DeepSeek-вызовы.

## Как готовить платный запуск после отдельного разрешения

После проверки отчёта и согласования бюджета изменить **только свои**
значения в локальном, игнорируемом Git `.env`:

```dotenv
REQUIREMENTS_LLM_MAX_CALLS=<approved_global_cap>
REQUIREMENTS_LLM_ATOMIZATION_CALLS=<approved_atomization_cap>
REQUIREMENTS_LLM_TARGETED_CALLS=<approved_targeted_cap>
```

Все три значения должны быть целыми неотрицательными числами,
общий cap — не менее 1. Важно: это максимальное **число запросов
приложения**, а не лимит денежных затрат или токенов; сетевой повтор
может приводить к нескольким оплачиваемым HTTP-попыткам.

Нельзя выбирать конкретный cap только по baseline 377: он
не включает вторичные matching-батчи, coverage, обратный поиск и аудит.
Если запустить без достаточного бюджета, итог может остаться неполным.

После изменения `.env` пересоздать API-контейнер, чтобы он получил
новые переменные. Для CLI можно разово задать
`--max-calls` и `--targeted-calls`, однако atomization-cap берётся
из `.env`.

**Не пополнять баланс и не выполнять API-запуски ради этой проверки.**
Реальный сквозной прогон исходной пары — отдельный этап после
явного разрешения.
