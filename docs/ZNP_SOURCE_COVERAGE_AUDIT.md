# P0 — полнота исходных фрагментов ЗнП (issue #54)

**Статус:** PR #55, осторожное исправление + диагностика. **Не считать полным решением до аудита исходного DOCX.**
Связанные задачи: #54, закрытый P0 #52 (родительский контекст), PR #51 (ID-доказательства, отдельно).

## Обнаруженная проблема

На исходном `zadanie_na_proektirovanie_pgu-236_urgres.docx`
локальный Codex увидел **1 329 исходных фрагментов**, но **313**
(262 абзаца, 38 заголовков, 12 табличных строк и один TOC)
не участвовали ни в `atom.sources`, ни в `atom.context_sources`.
Среди них встречается техническое приложение с параметрами и
ограничениями. Это одинаково было в `dev` до PR #53 и после его
контекстного исправления; **не новая регрессия**.

Причина, обнаруженная при изучении `extract_clauses`:
служебный заголовок может перевести парсер в `skip_section`,
а выход из него ограничен нумерованными **нетабличными** пунктами
с десятичной нумерацией. В частности, начинающийся с
`Приложение N. ...` заголовок ранее считался служебным,
и таблицы технического приложения могли полностью игнорироваться.
Это **подтверждённая возможность в коде**, но точные причины
каждого из 313 пропусков определит локальный аудит.

## Что изменено

1. В **консервативном извлечении ЗнП** заголовки нумерованных
   технических приложений больше не считаются автоматически
   служебными; `Приложение А. Перечень сокращений` остаётся
   исключённым. Наследованный не-консервативный путь ТУ не изменён.
2. Извлечённые положения технических приложений получают
   `appendix_scope_requires_review` и
   `context_scope_requires_review`: сохранённая таблица сама
   по себе не даёт автоматического `supports`.
3. `source_coverage_ledger` классифицирует **каждый** фрагмент
   ровно один раз:
   - `atom_source` — полный проверяемый текст в атоме;
   - `context_only` — только источник условия/заголовка;
   - `excluded` — только строго определённые пустые,
     служебные страницы, оглавление, очевидный шум;
   - `unclassified` — всё остальное, что никуда не попало;
     **не объявлять это автоматически несущественным**.
4. Короткая числовая строка или ячейка таблицы (например,
   `10`, `6`, `0,4`) **не** объявляется шумом.
5. В полной сверке сохраняется агрегат `trace_info.source_coverage`.
   Если есть `unclassified`, автоматические `fulfilled`
   становятся `needs_review`, confidence автоматического
   решения обнуляется, причина явно указывается в отчёте.
   Исторические снимки и подтверждения инженера не изменяются.
6. Перед платной полной сверкой фронтенд читает бесплатный
   `GET /api/v1/projects/{project_id}/comparisons/{pair_id}/source-coverage`.
   При непроверенных источниках показывает число и **запрашивает
   отдельное подтверждение**, что пользователь согласен оплатить
   анализ заведомо неполного извлечения. Тест 10×10 не меняется.
7. Сервер тоже проверяет это **до первого платного запроса**.
   Без `allow_incomplete_sources=true` возвращается HTTP 422
   без вызова DeepSeek. Явное подтверждение передаётся в
   `OperationRequest` и сохраняется в параметрах фоновой операции,
   поэтому не теряется после паузы/рестарта. Для прямого POST
   `/runs` это query-параметр. При разрешённом неполном запуске
   никакое автоматическое `fulfilled` всё равно не допускается.

## Локальная диагностика на оригинальном ЗнП (DeepSeek = 0)

Файл `backend/scripts/audit_znp_source_coverage.py` работает через
production DOCX-парсер и `atomize_fragments`, не обращаясь к
DeepSeek, embeddings и базе. Он пишет список всех исходных fragment
IDs с ролью, страницей, позицией, типом, container ID и хешем
текста, без исходного текста.

Запуск на Windows из backend virtualenv/контейнера, с аргументами:

```powershell
python -m scripts.audit_znp_source_coverage \
  --znp "D:\Sber\zadanie_na_proektirovanie_pgu-236_urgres.docx" \
  --out "D:\Sber\diagnostics\znp-source-coverage-pr55.json" \
  --private-review "D:\Sber\diagnostics\znp-source-unclassified-PRIVATE.jsonl"
```

В PowerShell перенос строк делается через backtick, не `\`;
вызов можно выполнить одной строкой. При работе с Docker
передавать исходный DOCX read-only, желательно `--network none`,
без API-ключа и доступа к рабочей базе. Файл `--private-review`
содержит **исходный текст всех непроверенных фрагментов**,
создаётся только по явному запросу и никогда не отправляется в GitHub.

### Задача локальному Codex

1. Зафиксировать неизменённый SHA исходного DOCX и точный
   SHA PR #55. Выполнить офлайн-аудит на оригинале.
2. Для всех прежних **313** фрагментов проверить роль
   в новом конвейере. Сравнить прежние `parent-pr53.json`
   и новый ledger по fragment IDs и SHA; IDs нового CLI намеренно
   совпадают с историческим `audit_znp_parent_scope.py`.
   Новые источники должны оставаться в исходном документе
   без догадок и генерации цитат.
3. Оставшиеся `unclassified` разделить по проверенному тексту:
   служебные/TOC, структурные заголовки, ограничения применения,
   требования, параметры таблиц, технические приложения, иное.
   **Не относить все 313 к требованиям автоматически.**
4. Проследить каждую существенную потерю до её причины:
   `skip_section`, неверный TOC, заголовок, отсутствие номера,
   `extract_clauses`, слияние таблиц или разбор формата.
   Вносить небольшие исправления с тестом на каждую реальную
   категорию, при необходимости в этот PR.
5. Для покрытых новых атомов проверить точные source offsets,
   `context_sources`, отсутствие подмены разных объектов и
   неприменимых условий. Нет новых `supports`/`fulfilled`
   без доказательств.
6. Сравнить число атомов, статус исключений, ID, список
   `unclassified`, параметры, полноту, предупреждения.
   При любых изменениях состава атомов считать checkpoints
   старой версии несовместимыми там, где изменён входной промпт.
7. Не делать никаких реальных запросов DeepSeek, пока
   существенные пропуски исходного текста не закрыты.
   Сырые фрагменты, диагностические JSON и исходные документы
   хранить только локально.

**Критерий завершения P0:** для каждого из 1 329 фрагментов
есть подтверждённая роль и причина; каждое содержательное
техническое ограничение представлено атомом или применимым
источником контекста, а непроверенные участки явно видны и
не позволяют выдавать автоматическое `fulfilled`.

## Ограничения первого этапа

- Новый классификатор намеренно **не делает вывод**, что
  отсутствующий абзац или заголовок несущественен. Поэтому
  могут появиться новые `needs_review`. Это защита от
  ложного успешного заключения, а не ошибка модели.
- Наличие идентификаторов таблиц не доказывает корректное
  применение ограничений между таблицами. Такое условие
  требует отдельной проверки.
- CI/моки не могут подтвердить, что все 313 пропусков
  восстановлены: оригинальный DOCX не хранится в GitHub.
- Следующий обязательный шаг — **локальная классификация всех
  непокрытых источников**, а не новый платный полный run.
