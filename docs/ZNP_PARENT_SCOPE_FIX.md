# P0: наследование родительского контекста ЗнП по разделам и таблицам

**Связано:** [#52](https://github.com/Barusss/Sber-Giga-Project/issues/52), PR #53.  
**Статус:** код и бесплатные регрессии, **проверка реальной исходной пары ещё не выполнена**.

## Причина

Ранее `backend/app/requirements/atomization.py` искал родительский пункт
через один глобальный словарь `previous_clauses[номер]`. В частности,
пункт `1.1` мог получить условие из `1` другой таблицы или другого
раздела, если нумерация начиналась заново. Проблема усугублялась тем,
что исходный DOCX-парсер не сохранял идентификатор таблицы: соседние таблицы
в одном разделе невозможно было структурно различить.

Ещё один независимо выявленный при регрессиях дефект:
`extract_clauses(..., conservative=True)` мог **склеить целиком**
пункт `1` одного раздела и пункт `1.1` другого, ещё до подбора
`context_sources`. Это также исправлено.

## Изменения

1. `ExtractedBlock.container_id` и `Fragment.container_id` —
   стабильный в пределах одного DOCX при одинаковом извлечении
   номер `docx-table-N`. В обычных абзацах и PDF значение `NULL`.
2. Новая миграция `0013` добавляет необязательное поле. Никаких
   старых исходных документов, страниц, цитат и исторических отчётов
   миграция не переписывает.
3. `extract_clauses` закрывает текущую группу при переходе
   между разными таблицами, при начале нового нумерованного пункта на
   границе таблицы и прозы, а также между несвязанными известными
   разделами. Ненумерованная строка новой таблицы сохраняется как
   самостоятельный консервативный атом. Ненумерованное примечание
   сразу после таблицы или перед ней **не теряется**: остаётся рядом
   с текстом требования и получает
   `mixed_table_prose_scope_requires_review`.
4. Родительский пункт сопоставляется **только внутри доказанной области**:
   совпадающего раздела или его структурного потомка; когда есть
   фрагмент заголовка, используется также **его точный ID**, а не
   только совпадающий текст `section_path`. Это отделяет два разных
   раздела с одинаковым названием. Для двух строк таблицы
   дополнительно требуется совпадающий непустой `container_id`.
   Нумерация сама по себе недостаточна. При повторениях в одной
   доказанной области берётся последний предшествующий родитель.
5. Если подходящий номер родителя встречался, но безопасная область
   наследования не установлена, чужой фрагмент **не включается**
   в контекст. Вместо этого сохраняются
   `parent_scope_unresolved` и `context_scope_requires_review`,
   блокирующие автоматический `supports`.
6. Поисковые `chunks` также не объединяют строки соседних таблиц
   в одном разделе. Для исторических строк без `container_id` чанки
   разделяются консервативно. Это может изменить количество embeddings
   при reindex, но исключает склейку заведомо недоказанного контейнера.
7. Условия родителей, полученных из действительно допустимой области,
   остаются точными `context_sources` с предупреждением о
   необходимости ручной проверки; защита `fulfilled` не менялась.

### Важная консервативная граница

Если строка исторической таблицы не имеет `container_id` или
раздел не определён, **автоматически приписать ей родителя нельзя**.
Это может увеличить число `needs_review`, но не должно создавать
ложное инженерное подтверждение. Сложные межтабличные вводные
условия требуют отдельной явной проверки области действия, а не
объединения по числу `1`.

## Существующие документы

Новая миграция добавляет `container_id=NULL` к историческим
фрагментам. **Сама по себе миграция не восстанавливает принадлежность
старых фрагментов к таблицам.**

Для уже загруженного DOCX при наличии неизменённого исходного файла
можно использовать существующий безопасный механизм:

`POST /api/v1/documents/{document_id}/reindex-chunks`

Он сверяет число, порядок и текст всех фрагментов с повторно
прочитанным исходником и отказывается при несовпадении. Теперь
он также заполняет `container_id`, **сохраняя существующие ID
фрагментов и ссылочные цитаты**. Поскольку перестраиваются
поисковые chunks, их прежние embeddings инвалидируются и будут
созданы повторно при необходимости.

Перед reindex сделать резервную копию базы и убедиться, что
проект допускает изменение документов. Не перезаписывать
вручную `section_path` или `container_id` и не обходить
проверку соответствия исходников.

## Бесплатные проверки

Регрессии проверяют:
- повтор `1` / `1.1` в разных разделах и двух соседних таблицах;
- незаполненный `container_id` у исторического DOCX;
- сохранение верного родителя во вложенном разделе;
- сохранение ненумерованных строк после разделителя;
- реальный парсер DOCX на документе из двух таблиц;
- запрет автоматического `supports` при
  `parent_scope_unresolved` даже с точными совпадающими цитатами;
- сохранность детерминированных идентификаторов атомов.

## Следующая проверка на оригинальных DOCX

На исходной паре `tu_2026_gu-236_urgres.docx` и
`zadanie_na_proektirovanie_pgu-236_urgres.docx` необходимо **без API**
запустить существующий `diagnose_deepseek_pair --dry-run`
(он теперь переносит `container_id` и возвращает
`parent_scope`: предупреждения, число таблиц и таблиц с подтверждённым
идентификатором). Никакие платные вызовы в `--dry-run` не выполняются.

Сравнить до/после: число атомов, распределение предупреждений,
исходные идентификаторы и источники родителя каждого дочернего
пункта, особенно повторения нумерации между таблицами.
Проверить выборочно минимум 10 разделов/таблиц с повторными номерами.
Сырые документы и диагностические фрагменты не коммитить.
Изменение числа атомов ожидаемо: ранее некорректно склеенные
пункты теперь разделяются.

Не заявлять об исправлении всех случаев родительской области
до предметной проверки на этой паре. Полный DeepSeek-run и
оценка `fulfilled` — отдельный шаг только с согласованным
платным бюджетом.


## Практический офлайн-аудит двух версий (без DeepSeek)

Добавлен `backend/scripts/audit_znp_parent_scope.py`. Он загружает оригинальный
ЗнП через production-парсер, строит консервативные атомы и записывает **только
ID фрагментов, номера пунктов, хеши и предупреждения**, без текста документа.
Скрипт не инициализирует DeepSeek и не подключается к БД.

Сравнивать нужно **одну и ту же исходную копию DOCX**, а не её заново
пересохранённую версию. У скрипта есть проверка `source_sha256`: разные
файлы сравнивать запрещено.

Для локального Codex на Windows:

1. Проверить `git status`. Не переключать ветку в пользовательском
   рабочем каталоге с незакоммиченными изменениями. Создать две временные
   `git worktree` рядом с репозиторием: для `origin/dev` и для
   `origin/fix/znp-parent-context-scope-20261121`.
2. Запустить **один и тот же файл** `audit_znp_parent_scope.py` в двух
   окружениях с соответствующими версиями кода. Для `dev` можно
   временно скопировать **только этот CLI-скрипт** из PR #53 во внешнюю
   диагностическую папку, не меняя его алгоритма.
3. Запуск базовой версии:

   ```powershell
   python audit_znp_parent_scope.py --znp "D:\Sber\zadanie_na_proektirovanie_pgu-236_urgres.docx" --out "D:\Sber\diagnostics\parent-dev.json"
   ```

   Использовать `PYTHONPATH` из `worktree` **dev**. Если зависимости
   есть только в Docker, запускать `docker run --network none` с
   read-only-монтированием исходного DOCX, скрипта и соответствующей
   директории `backend`; передать `PYTHONPATH` от смонтированного кода.
   Никакие ключи DeepSeek в контейнер не передавать.

4. Запуск PR #53 на **том же** файле и том же CLI:

   ```powershell
   python audit_znp_parent_scope.py --znp "D:\Sber\zadanie_na_proektirovanie_pgu-236_urgres.docx" --out "D:\Sber\diagnostics\parent-pr53-diff.json" --compare-before "D:\Sber\diagnostics\parent-dev.json"
   ```

   Здесь `PYTHONPATH` должен указывать на `backend` из PR #53.
   Дополнительно создать самостоятельный `parent-pr53.json` без
   `--compare-before`, чтобы можно было проверить каждый новый контекст.

5. Проверить два результата и вручную выборку **минимум 10 случаев**
   повторной нумерации / таблиц: правильный родитель, отсутствие
   «родителя» из другой таблицы, сохранность условий/альтернатив/
   исключений, а также обоснованность новых warnings. Для точной
   проверки предложенных ID разрешается смотреть исходный текст
   **только локально**, но не прикладывать его в GitHub.
6. Убедиться, что `lost_source_fragment_ids=[]`. Если фрагмент
   исчез из атомов, выяснить причину; не принимать PR с потерей
   требования или условия. Появившиеся `regrouped_fragment_ids`
   вручную проверить на границы таблиц и разделов.
7. Не считать число уменьшившихся предупреждений критерием успеха:
   недоказанный родитель обязан сохранять `parent_scope_unresolved`
   и не давать автоматический `supports`.
8. Зафиксировать в PR **только агрегированные числа**, список
   аномалий по неприватным ID, итог PASS / DO NOT MERGE и проверенный SHA.
   Отчёты `parent-*.json` и DOCX оставить в игнорируемом
   `D:\Sber\diagnostics`. **Вызовов DeepSeek: 0.**

**Ограничение:** этот CLI проверяет родительский контекст и состав атомов,
но не проверяет качество семантического matching и не является полным
сквозным тестом. PR #51 с evidence ID / strict проверяется отдельно.
