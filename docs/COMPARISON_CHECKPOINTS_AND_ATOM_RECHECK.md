# Возобновляемая сверка ТУ ↔ ЗнП и повторная проверка одного атома

**Реализация:** PR #50. **Статус:** первый этап отказоустойчивости, не гарантия exactly-once на стороне DeepSeek.
**Требования:** PostgreSQL + миграция Alembic `0012`. Текущий Docker Compose запускает один процесс Uvicorn.

## Что сохраняется

- Каждый платный `complete_json` получает стабильный отпечаток на основе полного
  системного/user-промпта, модели, thinking, `max_tokens` и версии формата
  чекпоинтов. Ответ модели с базовой проверкой структуры сохраняется в
  `comparison_llm_checkpoints` в **самостоятельной транзакции PostgreSQL**.
- Перед отправкой запроса записывается `status=sent`. После сохранения ответа
  он становится `succeeded`. Ошибка ответа помечается `failed`.
- При продолжении `succeeded` по тому же отпечатку воспроизводится локально:
  повторной оплаты API за него нет. Валидация цитат, параметров, контекста и
  окончательных решений выполняется повторно на текущем коде.
- Лимиты считаются **кумулятивно** по попыткам всего задания, включая
  предыдущие возобновления. Они не обнуляются после падения.
- Новые требования ТУ получают детерминированные ID на основе исходного
  содержимого: до финальной транзакции временные ID не меняются при restart.
- Завершённый `ComparisonRun` и изменения текущих подтверждений/замечаний
  фиксируются атомарно. У снимка есть ссылка на `operation_job_id`, поэтому
  перезапуск после коммита не создаёт второй опубликованный снимок.

## Пауза, продолжение и восстановление

В панели операций для сверки появились **Пауза**, **Продолжить** и
**Завершить без продолжения**.

- Пауза действует кооперативно, **после завершения текущего запроса/этапа**.
  Она не прерывает уже отправленный HTTP-запрос в середине и не удаляет результаты.
- После ошибки DeepSeek задание переходит в `paused`: сохранённые успешные
  запросы остаются. После настройки баланса, сети или лимитов — `Продолжить`.
- При перезапуске **единственного** процесса API незавершённые jobs восстанавливаются
  из PostgreSQL. Если последний запрос остался `sent`/ `failed`, задание
  останавливается на паузе и **не повторяет вызов автоматически**.
- Если запрос уже был передан DeepSeek, но ответа/коммита нет, мы **не можем
  узнать, списал ли провайдер деньги**. UI требует явного подтверждения риска
  повторного списания. Претензий на exactly-once billing нет.
- Возобновление пересоздаёт локальный поиск и состояние алгоритма, но
  дорогостоящие уже сохранённые запросы перепроигрываются из базы.
  Физически это не продолжение Python-стека с той же строки.
- При остановке между публикацией готовой пары и обновлением фонового статуса
  ссылка `operation_job_id` позволит восстановить результат пары без повторной
  публикации. Для пакетной сверки завершённые пары пропускаются.
- Старые запуски, выполненные до миграции `0012`, нельзя восстановить на
  уровне отдельных вызовов: эти ответы никогда не сохранялись.

**Внимание:** текущая реализация ориентирована на **один процесс API** из
`docker-compose.yml`. Для нескольких независимых API-инстансов нужно
отдельно реализовать/протестировать распределённое владение заданиями,
lease/heartbeat и fencing. Простое увеличение `uvicorn --workers`
без этого запрещено.

## Повторный DeepSeek-запрос для конкретного ЗнП

В отчёте на вкладке «ЗнП → ТУ» у каждого положения с сохранёнными
`sources` доступна кнопка **Повторить ИИ-проверку ЗнП**.

- В новом фоновом задании собираются кандидаты ТУ и выполняется **одна
  независимая первичная модельная проверка выбранного атома**.
- Возвращённые связи проходят ту же проверку исходных непрерывных цитат,
  объектов, инженерных параметров и предупреждений контекста.
- Результат сохраняется **отдельно**, в `comparison_atom_reviews`, с
  датой и историей предыдущих перепроверок. Отображается под соответствующим
  положением.
- **Не меняет опубликованные статусы**, покрытие обязательств ТУ,
  аудит противоречий, решения инженера или предыдущие снимки. Применять
  такие связи к итоговым вердиктам можно только через полную пересверку
  либо после отдельного проекта точечной переоценки всех зависимостей.
- Старые снимки без достаточных исходных фрагментов не допускаются к
  безопасной точечной перепроверке. Кнопка недоступна до нового полного запуска.
- Повторный запуск создаёт **новую** платную проверку; остановка/продолжение
  **этого же** фонового задания использует его сохранённые checkpoint-ответы.

## API

- `POST /api/v1/projects/{project_id}/operations/{job_id}/pause`
- `POST /api/v1/projects/{project_id}/operations/{job_id}/resume`
  с JSON `{"accept_replay_risk": false}` (для неопределённой отправки
  сервер возвращает 409, пока пользователь явно не подтвердит `true`).
- `POST /api/v1/projects/{project_id}/operations` с
  `{"kind":"comparison_atom_recheck","pair_ids":["PAIR_ID"],
    "run_id":"RUN_ID","atom_id":"ATOM_ID"}`
- `GET /api/v1/projects/{project_id}/comparisons/{pair_id}/runs/{run_id}/atom-reviews`
  (опциональный параметр `atom_id`).

## Обязательные проверки перед эксплуатацией

1. `alembic upgrade head` на резервной копии локальной БД.
2. `pytest -q` (включая fault-injection для `sent` без ответа,
   persisted `succeeded`, pause/resume, миграции и API перепроверки ЗнП).
3. Проверить в браузере паузу после успешного matching, рестарт контейнера
   и продолжение того же ID операции.
4. Сравнить количество вызовов провайдера до/после restart на контролируемой
   заглушке. На настоящем API делать это **только после согласования бюджета**.
5. Убедиться, что текущий опубликованный снимок не меняется до полной
   успешной пересверки.

Сохраняемый ответ модели содержит производную информацию из документов:
доступ к PostgreSQL и его резервным копиям должен быть защищён как к самим ТУ/ЗнП.

## Что ещё нужно для максимально надёжной промышленной эксплуатации

- Мультипроцессный worker-lease, heartbeat и fencing при использовании
  нескольких API-инстансов.
- Долговременные локальные checkpoints OCR/embeddings (сейчас при restart
  подготовительные локальные этапы пересчитываются).
- Раздельные политики ограниченного retry для каждого класса ошибок и
  контроль денежного бюджета провайдера по токенам, а не только числу
  запросов.
- Нагрузочные испытания на 300/1000/нескольких тысячах атомов и отдельные
  полноценные реальные API-испытания. CI с фейковой моделью их не заменяет.
