# Проверка актуальности ГОСТ: локальный реестр и Росстандарт

Проверка **не использует DeepSeek для определения статуса**. Статус берётся из локального реестра `normatives`, а при отсутствии пригодной записи — с официального портала https://protect.gost.ru/gost, раздел «ГОСТ, ГОСТ Р, ПНСТ».

## Порядок проверки

1. Для каждого найденного обозначения нормализуется код и ищется запись в локальном реестре.
2. Если в реестре есть статус `active` или `obsolete`, он используется **без сетевого запроса**. Это основной режим: проверка остаётся доступной, когда сайт Росстандарта недоступен.
3. Если записи нет или её статус `unknown`, выполняется запрос к Росстандарту. Для ГОСТ ищется точное обозначение, загружается карточка и проверяется совпадение обозначения в заголовке и поле «Обозначение». Из карточки читаются статус, название, «Обозначение заменяющего» и URL. Поиск по похожему названию не допускается.
4. Подтверждённый официальный статус сохраняется в локальный реестр вместе с `checked_at` — датой подтверждения. При следующей проверке эта запись снова используется локально.

Источник и дата всегда возвращаются в ответе:

- `source=local` — статус из локального реестра, `checked_at` мог быть получен ранее или отсутствовать у ручной записи;
- `source=rosstandart` — статус подтверждён официальной карточкой сейчас;
- `source=unknown` — пригодного статуса нет.

Локальный статус не выдаётся за свежую официальную проверку: `checked_at` не подменяется текущим временем. Если дата неизвестна, интерфейс и отчёт так и пишут.

## Принудительное обновление

По умолчанию локальная запись не перезапрашивается. Чтобы обновить её из Росстандарта, передайте query-параметр:

```http
POST /api/v1/documents/{document_id}/check-normatives?refresh=true
```

В интерфейсе это кнопка **«2b. Обновить из Росстандарта»**. При `refresh=true`:

- официальный запрос выполняется даже при наличии локальной записи;
- при успехе локальная запись обновляется, `source=rosstandart`;
- при недоступности сайта сохраняется локальный статус с `reason=refresh_failed_local_fallback` и прежним `checked_at`;
- если локальной записи нет, результат остаётся `unknown`.

## Как проверить уже загруженный ГОСТ

1. Обновите репозиторий: `git pull origin main`.
2. Запустите `docker compose up -d --build api web`.
3. В `http://localhost:8000/docs` проверьте, что документ уже имеет `normative_reference` через `GET /api/v1/documents/{document_id}/facts?fact_type=normative_reference`.
4. Выполните **POST** `/api/v1/documents/{document_id}/check-normatives` без тела запроса. Для принудительного обновления добавьте `?refresh=true`.
5. Ответ содержит `total`, `active`, `obsolete`, `unknown`, `findings_created`, `findings_already_existing` и массив `checked` со статусом, источником, заменой и страницами PDF.
6. Результаты также видны на вкладке **ГОСТ и НТД**: выберите проект, затем документ из выпадающих списков, нажмите **Извлечь** (при необходимости) и **Проверить актуальность**. Вводить технический ID вручную не требуется.
7. Откройте **GET** `/api/v1/projects/{project_id}/normative-report` или **GET** `/api/v1/projects/{project_id}/findings`: замечания о недействующих ГОСТ записываются туда с цитатой и ссылкой на источник. У замечаний `review_status=pending`. Повторный запуск не создаёт новых копий.

**Контрольный пример:** официальная карточка ГОСТ 29322-92 — https://protect.gost.ru/gost/details/ddd080ed-1dd3-41bd-8cf7-f55a18dc2c5e . В реестре указан статус «Заменен», заменяющий стандарт «ГОСТ 29322-2014». После успешной официальной проверки запись сохраняется локально; при следующей проверке используется без обращения к сайту.

## Локальный реестр

Реестр доступен через `/api/v1/normatives` и редактируется в интерфейсе. Это **не полный каталог ГОСТов**, а набор записей, которые уже подтверждались или были добавлены вручную.

- `checked_at` заполняется только при подтверждении официальной карточкой. У ручной записи дата может отсутствовать — это нормально и отображается явно.
- `registry_status` хранит буквальную категорию сайта (например, «Заменен»). Для ручных записей он может быть пустым.
- При ручном изменении `status` или `source_url` прежние `checked_at` и `registry_status` сбрасываются: старая официальная дата больше не соответствует новому статусу.
- Устаревшую локальную запись можно обновить кнопкой **«2b. Обновить из Росстандарта»** или параметром `?refresh=true`.

## Важные ограничения и поведение

- Для официального поиска поддерживаются полные обозначения `ГОСТ ...-год` и `ГОСТ Р ...-год` (включая варианты с ИСО/МЭК). Обозначения без года, IEC/EN, СП, СНиП при отсутствии локальной записи получают `unknown`: нельзя безосновательно приписывать им статус из фонда ГОСТ. Если такая запись добавлена в локальный реестр вручную, используется она.
- Разрешены только `protect.gost.ru` и точные URL карточек `/gost/details/{uuid}`; автоматические переходы на другие сайты запрещены. Входной `source_url` из локального реестра используется лишь как подсказка и при официальной проверке перечитывается.
- Ошибка сети, изменение структуры официальной страницы, неуверенный результат поиска или неоднозначный статус без локальной записи дают `unknown`. **Система не угадывает статус и не ставит текущую дату вместо даты подтверждения.**
- `status` — `active / obsolete / unknown`. Для «Принят» и «Действует с ограничением» возвращается `unknown`, чтобы не называть стандарт безусловно действующим.
- Замечания `obsolete_normative` создаются при статусе «Заменен», «Отменен», «Срок действия истек» или «Утратил силу в РФ» — как из официальной карточки, так и из локальной записи. Ссылка из справочного раздела получает уровень `info`, нормативная — `warning`. В тексте замечания явно указано, откуда взят статус.
- Повторный запуск не создаёт дубликатов замечаний. Принятые и отклонённые замечания сохраняются для аудита. Изменение статуса ГОСТ не означает автоматическое удаление старых замечаний: их нужно пересмотреть вручную.
- Проверка не требует ключа DeepSeek и не делает вызовов к языковой модели.
- Максимум 50 различных обозначений на один запуск; обработка пока синхронная. У сайта нет подтверждённого документированного публичного API, поэтому используется чтение HTML. При изменении сайта обработчик перестаёт подтверждать новые статусы, но продолжает использовать уже сохранённые локальные записи.

Не следует автоматически заменять ссылку только потому, что обнаружена новая редакция. Применимость, требования договора и нормативная обязательность требуют отдельной оценки.

## Тесты

```powershell
cd backend
pytest tests/test_normative_verification.py tests/test_expert_normative_report.py tests/test_migrations.py -q
```

Сетевые ответы для тестов замоканы. Тесты проверяют извлечение статуса/замены, безопасность адресов, локальный приоритет без сетевого запроса, отказ от выдумывания статуса при недоступности сайта, принудительное обновление, сохранение и повторную проверку. Работа с живым сайтом проверяется отдельно при запуске у пользователя; успешные unit-тесты не гарантируют сетевую доступность или стабильность HTML-формата.
