# Автоматическое извлечение нормативных ссылок через DeepSeek

## Быстрая проверка на уже загруженном документе

1. Скопируйте корневой `.env.example` в `.env`, установите `DEEPSEEK_API_KEY=...`. Ключ не должен попадать в Git или frontend.
2. Перезапустите backend: `docker compose up -d --build api`.
3. Откройте `http://localhost:8000/docs`.
4. Выполните **POST** `/api/v1/documents/{document_id}/extract-facts` без тела запроса. Для ранее загруженного ГОСТ 32144-2013 ID документа: `4025b378-d38c-4c7b-bb72-a565028b145c` (только в локальной базе, где он уже загружен).
5. Проверьте результат: `created`, `scanned_chunks`, `deepseek_calls`, `facts[].value.code`, `facts[].evidence[].page`. Затем вызовите **GET** `/api/v1/documents/{document_id}/facts?fact_type=normative_reference`.

## Алгоритм

- Проходит **все chunks** документа по порядку (нет ограничения первыми страницами), читает исходные `fragment` по `chunk_sources`.
- Регулярным выражением отбирает буквальные обозначения ГОСТ/ГОСТ Р, СП, СНиП, ПУЭ, ISO/IEC/EN; каждому кандидату назначает ID и реальную цитату с `fragment_id` и страницей.
- Передаёт кандидатные цитаты (пачками до 25) в DeepSeek для решения, является ли выражение нормативной ссылкой, а не колонтитулом, названием самого документа или мусором.
- **Модель возвращает только номера кандидатов.** Код норматива, цитата, страница и `fragment_id` в базе берутся строго из исходных данных, не из сгенерированного текста.
- Один факт `normative_reference` создаётся на одно обозначение; повторные упоминания одного обозначения сохраняются как несколько `fact_evidence`.
- Повторный запуск не дублирует уже сохранённые обозначения в этом документе. Ранее сохранённые/проверенные факты не перезаписываются.
- Запись происходит только после завершения **всех** вызовов DeepSeek; ошибка посредине не создаёт частичный результат.

Ограничение: до 500 кандидатов на запуск (HTTP 413 для более крупных документов). Обработка пока синхронная, поэтому для крупных PDF возможна длительная работа. Число вызовов DeepSeek и стоимость зависят от числа кандидатов. Пустой `DEEPSEEK_API_KEY` при необходимости вызова модели даёт HTTP 503, ошибки DeepSeek — HTTP 502.

Результат содержит `document_id`, `scanned_chunks`, `candidates`, `deepseek_calls`, `created`, `skipped_existing`, `skipped_invalid` и `facts`. `review_status` новых фактов — `pending` для проверки человеком.

## Границы MVP

Это **извлечение ссылок на нормативы**, а не проверка их статуса/актуальности. Например, «ГОСТ 29322» и «ГОСТ 29322-92» сохраняются как разные обозначения: связь редакций потребует отдельной логики сверки с реестром Росстандарта. OCR может ошибаться в формулах и таблицах; найденные ссылки нужно перепроверять. Регулярное выражение может пропустить необычные или разорванные переносами обозначения.

**Безопасность:** вызов платного API доступен на тестовом backend без авторизации. Не публикуйте порт 8000 в интернет, пока не добавлены авторизация и лимиты запросов; отправляйте внешнему сервису только документы, для которых это разрешено.



## Нормализация и классификация (v2)

После обновления кода снова вызовите **POST** `/api/v1/documents/{document_id}/extract-facts` на прежнем документе. **Повторно загружать PDF не нужно**. Изменения применяются только к фактам, автоматически созданным предыдущей версией и оставшимся в статусе `pending`:

- Базовое обозначение ГОСТ без года (например, `ГОСТ 30804.4.30`) объединяется с полным обозначением (`ГОСТ 30804.4.30-2013`) **только когда в документе встречается ровно один год редакции**. При нескольких годах базовая ссылка остаётся отдельным фактом, поскольку её нельзя однозначно отнести к редакции.
- Самообозначение документа (например, `ГОСТ 32144-2013` в ГОСТ 32144-2013) исключается при наличии обоснованного распознавания обложки или имени файла. Старые непроверенные факты с собственным номером удаляются.
- Для ссылок вычисляется `reference_kind`: `normative` (раздел «Нормативные ссылки» или основной текст требований) и `informative` (предисловие, содержание, библиография). Поле `contexts` показывает происхождение: `foreword`, `contents`, `normative_references`, `body`, `bibliography`. Если одно обозначение встречается в обоих контекстах, роль `normative` имеет приоритет.
- `variants` хранит встреченные формы записи, включая редакции с годом и ссылки без года. Исходные `evidence` с `fragment_id`, цитатой и номером страницы сохраняются.
- Существующие ручные факты и факты со статусом `accepted` или `rejected` **не изменяются и не удаляются автоматически**.
- В ответе появились поля `skipped_self`, `merged_duplicates`, `removed_self_facts`, `reclassified_existing`. Массив `facts` по-прежнему содержит только **новые**, а не обновлённые факты. Полный актуальный список: `GET /api/v1/documents/{id}/facts?fact_type=normative_reference`.

Роли получаются из позиции текста и заголовков и являются **эвристикой**, а не юридической оценкой обязательности требований. Например, при отсутствии распознанных заголовков и испорченном OCR классификация может быть неточной. Статус действия, отмена и замена стандартов **не проверяются** в этом шаге: для этого нужен официальный источник и отдельная логика сверки.
