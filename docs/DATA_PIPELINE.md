# Хранение OCR, поиск и факты (контракт между участниками)

## Поток данных

`PDF/DOCX -> fragments -> chunks -> [поиск] -> facts -> findings (согласование инженером)`.

- `documents`: оригинальный файл на диске; `extraction_version` позволяет отличить старые импорты (`ocr-v1`) от нового парсинга (`ocr-v2`).
- `fragments`: последовательные блоки текста страницы, `page` (1-based), `position` на странице, `block_type`, `section_path`, `bbox` из PDF-координат и `extraction_method` (`text`/`ocr`/`legacy`). Для DOCX физическая пагинация **неизвестна**: `page=1` — технический маркер, не основание утверждать, что цитата находится на первой физической странице.
- `chunks`: небольшие поисковые блоки (до 1400 символов), могут объединять соседние `fragments` и несколько страниц. `chunk_sources` содержит точные диапазоны символов исходных фрагментов. Размер и стратегия зафиксированы `chunking_version`.
- `facts`: структурированные типы (`fact_type`) и значения в JSON/JSONB, статус ручной проверки, оценка уверенности (не является вероятностью), версия извлекающего алгоритма. `fact_evidence` содержит реальные цитаты и ссылки на исходные `fragments`; один факт может опираться на несколько источников.
- `findings`: отдельная сущность **замечания** инженеру; факт сам по себе не является замечанием.

Предусмотренные типы фактов: `power_limit`, `connection_point`, `completion_deadline`, `normative_reference`, `technical_requirement`. Добавлять новые типы можно без SQL-миграции; структура `value` согласуется командой и версионируется через `extraction_version`. Не делать таблицу на каждый вид факта.

## Поиск

`POST /api/v1/documents/{id}/search`: текстовая часть работает сразу после загрузки документа; в PostgreSQL используется индексированная русская полнотекстовая выдача + поиск точных подстрок (для технических обозначений). SQLite — облегчённый поиск для тестирования.

Для semantic/hybrid search участник сам создаёт **384-мерные embeddings одной и той же моделью** и через `PUT /documents/{id}/chunks/{chunk_id}/embedding` заполняет векторы. Затем отправляет такую же модель и query embedding в `/search`. Сервер объединяет текстовую и векторную выдачу по reciprocal rank fusion. pgvector нужен только в PostgreSQL (Docker использует образ с extension), в SQLite векторные запросы возвращают 501. **Автоматической генерации embeddings и LLM-извлечения фактов в этом PR нет**, поэтому нельзя считать, что семантический поиск начнёт работать сам по себе.

Отдельно модуль ТУ/ЗнП использует необязательные локальные embeddings (`fastembed`, `EMBEDDING_ENABLED`) для гибридного поиска по пунктам. Векторы считаются в памяти запроса и **не записываются** в `chunks`/pgvector; при отключённой модели остаётся лексический канал.

Извлечение фактов — ответственность предметных модулей. Они обязаны подтверждать факты цитатой, которая действительно содержится в одном из исходных фрагментов. `confidence` — необязательное поле, не доказательство корректности. Для решения «требование отсутствует в ЗнП» одного пустого search-result недостаточно: выполняется дополнительная проверка всего релевантного документа.

## Пример: 3 факта на страницах 1, 45, 89

1. Загружаем 100-страничный документ один раз. OCR/парсер создаёт фрагменты и chunks, **по всему документу**.
2. Участник извлекает `power_limit`, `connection_point`, `completion_deadline` независимыми запросами к **всему** набору chunks (не к первым 10 страницам).
3. Сохраняет три `facts` с `evidence.fragment_id` и `quote`. Один факт может содержать несколько цитат с разных страниц.
4. При следующей проверке читаем готовые facts через `GET /documents/{id}/facts?fact_type=...`, при отсутствии нужного типа выполняем новый поиск.

## Согласование

Участник 1 владеет `documents/parser.py`, `documents/chunking.py` и загрузкой/хранением. Общий retrieval API находится в `app/search`; изменения схемы и API необходимо согласовывать с двумя другими участниками. Участники 2 и 3 пишут свои извлекатели и проверяющие модули; не копируют chunks или OCR в персональные таблицы.

Для загрузок после миграции новый парсер сохраняет блоки. `0002` индексирует уже имевшиеся `fragments` в chunks без повторного OCR. Старые цитаты сохраняют свой исходный `fragment_id`. Не делать повторный OCR без явно запланированной переиндексации.

**Ограничения MVP:** нет фоновой очереди (очень большие файлы обрабатываются в запросе), авторизации пользователей и автоматической проверки качества OCR. OCR изображений внутри смешанных PDF пока определяется эвристически, DOCX не рендерится на физические страницы. Для продуктивной эксплуатации потребуются отдельные процессы индексации, контроль доступа и тестирование качества поиска.
